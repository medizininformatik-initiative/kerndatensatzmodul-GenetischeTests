# Release Preparation Command

You are helping prepare a new release for the MII Molekulargenetischer Befundbericht module following the official MII Module Release Workflow.

## Usage

```
/release-prepare <VERSION>
```

Example: `/release-prepare 2026.0.0-rc.2`

The VERSION parameter is optional. If not provided, ask the user for it.

## Your Task

Execute Phase 1-3 of the MII Module Release Workflow:

### Phase 1: Create Release Branch

1. Check current git status - ensure working tree is clean (or stash changes)
2. Check current branch (main or dev depending on repo setup)
3. Get VERSION from command arguments, or ask user if not provided
4. Validate against `^\d{4}\.\d+\.\d+(-[0-9A-Za-z.-]+)?$` — CalVer with an optional
   SemVer prerelease suffix. The older three-pattern check rejected
   `2027.0.0-ballot.rc1`, which is the form this module actually ships. The same
   regex is assertion M6 in `scripts/convention-check.mjs`; keep them identical.
5. **Check for an existing release branch first** — `git branch --list 'release/*'`.
   Do not create a second one: this repo has used `release/{VERSION}` without the
   `v` since the 2027 line, while older branches carry it. Reuse what is there.
   The branch name is not what triggers the release — the tag is.

### Phase 2: Update Version Information

Update version numbers in these files:

1. **package.json**:
   - Update the `version` field
   - Update `description` with version highlights and link to release notes:
     ```
     "description": "Medizininformatik Initiative - Modul Molekulargenetischer Befundbericht. Version X.X.X: [key changes]. Release Notes: https://simplifier.net/guide/MII-Modul-MolekulargenetischerBefundbericht-v2026-DE/MIIIGModulMolekulargenetischerBefundbericht/ReleaseNotes"
     ```
2. **sushi-config.yaml**: Update the `version` parameter
3. **input/fsh/rulesets/version.fsh**: Update version in all three RuleSets:
   - `Version` ruleset
   - `PR_CS_VS_Version` ruleset
   - `MetaProfile` ruleset
4. **`.claude/config.json`** (`ig_export.version` and `ig_export.dependencies`): no
   build tool reads it, so it drifts silently, but `/build-package` names the
   tarball from it.

**Do NOT touch `implementation-guides/**/guide.yaml`.** Those trees are the retired
Simplifier sources; `implementation-guides/README.md` states they must not be
edited, and editing them changes nothing in the rendered guide.

IMPORTANT: Read each file first to verify current state before making changes.

### Phase 3: Run SUSHI

**CRITICAL**: After updating version files, run `sushi` to regenerate all FHIR resources with the new version. This updates the version in all StructureDefinitions and ValueSets.

```bash
sushi
```

Add all regenerated `fsh-generated/` files to the commit.

### Phase 4: Update Release Notes

1. The changelog is `input/pagecontent/changes.md` **and its German mirror**
   `input/translations/de/pagecontent/changes.md` — both must say the same thing.
   `ReleaseNotes.page.md` under `implementation-guides/` is retired; writing there
   has no effect on the guide.
2. Check git log for changes since ballot/last release:
   ```bash
   git log --oneline <last-ballot-commit>..HEAD
   ```
3. Update release notes with:
   - Ballot response items (HDB-XXX)
   - New features/profiles
   - Terminology changes
   - CI/CD improvements
   - Breaking changes

### Phase 5: Create Commit, Push, and Create PR

After all changes:
1. Stage all modified files including `fsh-generated/`
2. Create commit with message: `chore: Prepare release v{VERSION}`
3. Push the release branch: `git push -u origin release/{VERSION}`
4. Create pull request using gh CLI:
   ```bash
   gh pr create --base main --head release/{VERSION} --title "Release {VERSION}" --body "Release preparation for {VERSION}. See input/pagecontent/changes.md for details."
   ```
5. Provide the PR URL to the user

### Safety Checks

Before starting:
- Check for uncommitted changes: `git status --porcelain`
- If changes exist, offer to stash them: `git stash push -m "WIP before release" --include-untracked`
- Pull latest changes from remote

Files that should NOT be committed:
- `.bake/` (build artifacts)
- `package.bake.yaml` (local config)
- PDF files or other temporary documents

### Files to Update Checklist

- [ ] `package.json` - version and description
- [ ] `sushi-config.yaml` - version
- [ ] `input/fsh/rulesets/version.fsh` - both RuleSets
- [ ] `.claude/config.json` - `ig_export.version` and `ig_export.dependencies`
- [ ] `input/pagecontent/changes.md` + `input/translations/de/pagecontent/changes.md` - changelog, both languages
- [ ] `fsh-generated/` - regenerated by sushi

## Context

The MII Module Release Workflow has 8 phases total. This command handles phases 1-4 (automated preparation). The remaining phases:
- Phase 5: Create PR and wait for CI validation
- Phase 6: Merge PR and create tag (use `/release-finalize`)
- Phase 7-8: publishing. Since the template migration this module publishes through
  `.github/workflows/module-release.yml` (triggered by the tag) and `go-publish`,
  not through Simplifier. `/release-simplifier` and `/publish-simplifier` describe
  the old route and are kept only for the pre-2027 releases.

Refer to: https://github.com/medizininformatik-initiative/kerndatensatz-meta/wiki/Module-Release-Workflow
